# Участие в разработке

## Правило, определяющее весь процесс

**Текст подсказки для языковой модели является кодом.**

Он хранится в системе контроля версий, проходит проверку изменений и покрыт
тестами наравне с исполняемым кодом. Из этого следует, что правка текста
подсказки, манифеста витрин или правил проверки запросов проходит тот же путь,
что и правка модуля на Python: ветка, запрос на слияние, прогон проверок.

Без этого правила любое изменение подсказки превращается в лотерею: исправление
одного вопроса ломает три других, и разработчик узнаёт об этом от пользователей.

## Подготовка окружения

```bash
git clone https://github.com/devAsmodeus/dwh-copilot.git
cd dwh-copilot

python -m venv .venv
source .venv/bin/activate        # в Windows: .venv\Scripts\activate

pip install -e ".[dev]"
```

Развёртывание демонстрационного стенда:

```bash
cp .env.example .env
docker compose up -d
```

## Проверки перед отправкой изменений

```bash
ruff check .            # стиль кода
ruff format .           # форматирование
mypy                    # проверка типов
pytest                  # модульные проверки

python -m dwh_copilot.eval_runner --check-only    # целостность набора вопросов
```

Полный прогон набора бизнес-вопросов требует запущенного стенда и сервера
вывода модели:

```bash
python -m dwh_copilot.eval_runner --output eval/results/run.json --min-accuracy 0.70
```

## Требования к изменениям

### Изменение текста подсказки или манифеста витрин

Требуется прогон набора бизнес-вопросов до и после изменения. В описании
запроса на слияние приводятся обе величины доли верных ответов. Снижение
относительно достигнутого уровня является основанием для отклонения.

### Изменение правил проверки запросов

Каждое новое правило сопровождается двумя проверками: запрос, который правило
обязано отклонить, и запрос, который правило отклонять не должно. Вторая
проверка не менее важна первой: избыточно строгое правило делает систему
бесполезной так же надёжно, как отсутствующее правило делает её опасной.

### Добавление витрины

1. Создать представление в `sql/02_views.sql`.
2. Описать витрину в `config/views.yaml`, включая назначение, колонки
   и примеры значений категориальных полей.
3. Добавить не менее одного примера запроса в `config/examples.yaml`.
4. Добавить не менее одного вопроса в `eval/questions.yaml`.

Состав колонок в манифесте обязан совпадать с определением представления.
Расхождение обнаруживается сверкой и приводит к выводу витрины из перечня
разрешённых объектов до ручной вычитки.

### Добавление примера в банк запросов

Примеры пополняются по итогам эксплуатации: ответ, проверенный и подтверждённый
аналитиком, добавляется в `config/examples.yaml`. Эталонный запрос обязан
проходить модуль проверки безопасности и выполняться на демонстрационном стенде.

Ошибка в эталонном примере распространяется на все последующие ответы модели,
поэтому примеры проверяются внимательнее обычного кода.

## Стиль кода

- Строка не длиннее 100 символов.
- Строки документации обязательны для всех общедоступных функций и классов.
- Комментарии объясняют **почему** принято решение, а не **что** делает код.
- Английские термины при первом упоминании расшифровываются по-русски.
- Проверка стиля выполняется инструментом ruff, настройки в `pyproject.toml`.

## Сообщения коммитов

Применяется формат Conventional Commits. От него зависит автоматическое
определение номера версии при выпуске.

```
feat: добавлена витрина остатков по складам
fix: исправлен разбор имён из четырёх частей
docs: описан порядок обновления метаданных
chore: обновлены зависимости
```

Правила определения номера версии:

| Префикс | Изменение версии |
|---|---|
| `fix:` | младший разряд, например 0.1.0 в 0.1.1 |
| `feat:` | средний разряд, например 0.1.1 в 0.2.0 |
| `BREAKING CHANGE:` в теле | старший разряд, например 0.2.0 в 1.0.0 |

Выпуск версии выполняется автоматически: инструмент release-please накапливает
изменения в черновике запроса на слияние и ведёт файл CHANGELOG.md.

## Обновление зависимостей

Обновления отслеживаются автоматически и поступают еженедельно в виде запросов
на слияние. Каждый такой запрос проходит полный набор проверок.

Крупные версии библиотеки sqlglot обновляются вручную: от разбора запросов
зависит вся система проверки безопасности, и смена поведения разбора требует
отдельного рассмотрения.
